## v0.18.0（下一个 App 版本）

### 1. 历史问题收尾

- [ ] **重做吮吸滑条首次点击修复（原 PR #8）**。任务说明见 `AGENT-WORKFLOW.md` §0.3，原样有效。
- [ ] **优雅停机 + App 提示**
  - 问题：关停时 uvicorn 一直等 WS 连接关闭，直到 systemd 超时 SIGKILL，每次重启约 90 秒不可用；
    手机端只看到「已断开」，用户不知道发生了什么。
  - 服务端：lifespan 退出时向每台在线手机发送 `{"type":"server_shutdown","reason":"restart"}`，
    随后 `stop_all`，再以 close code 1012（Service Restart）主动关闭连接。
  - App：收到 `server_shutdown` 或 close code 1012 时，显示「服务器正在更新，马上自动重连」
    （Snackbar 加持续状态），不报错误；重连成功后自动消失。急停照常执行，**设备安全优先于体验**。
  - 验收：服务端测试断言关停时手机依次收到 `server_shutdown` → `stop_all` → close 1012；
    App 测试断言 1012 不显示为错误；生产重启数秒内完成，journal 中不再出现 `SIGKILL`。
- [ ] **CORS**：客户端只有原生 App 和 MCP 客户端，没有浏览器调用方，直接移除 `CORSMiddleware`，
    消除 `allow_origins=*` + `allow_credentials` 的组合（K8）。
- [ ] **命名残留**：代码里的 `Signal Bridge Remote`（7 个文件、systemd 描述）统一改为 AI-intoU（K6）。
    `server/` 的 MIT 署名声明保留不动。
- [ ] **生产部署从 git tag 拉取**，不再手工拷文件；清理部署目录里的 `*.bak*` 和游离文件；
    删除 `.env` 中已失效的变量（`doctor` 会逐条提示）。

### 2. App 内检查更新

> ⚠️ 已被 **v0.19.0 第 5 节**取代（GitHub Releases + 镜像源路线）；下文的清单 / Ed25519 方案不再实施，仅保留作历史记录。

- 问题：用户目前只能去 GitHub Releases 手动下载新版本。
- 思路借鉴 RikkaHub：清单 JSON + 版本号比较 + 系统 DownloadManager 下载。
  **RikkaHub 是 AGPL，只参考工程思路，代码自行编写。**
- 服务端：
  - 发版 CI 生成 `release/latest.json`（版本号、versionCode、发布时间、更新说明、APK 地址、sha256、大小、
    最低兼容版本），连同 APK 一起发布到更新路径。
  - 清单使用 **Ed25519 签名**；私钥只存在于 CI secret 中，App 内置公钥。
- App：
  - 设置页「检查更新」，冷启动时最多每 24 小时静默检查一次。
  - 有新版本时弹窗显示版本号和更新说明（Markdown 渲染）。
  - 下载后依次校验：清单签名、APK sha256、**APK 签名证书与当前已安装 App 一致**，
    全部通过才调起系统安装器（需要 `REQUEST_INSTALL_PACKAGES` + FileProvider）。
  - `min_supported` 高于当前版本时，弹窗不可跳过。
- 验收：清单被篡改、APK 被替换、APK 用其他证书签名，这三种情况都拒绝安装且有测试覆盖；
  无网络或清单 404 时静默失败，不打扰用户。

### 3. 安全加固

- 目标：让「拿 Release 包二改、重签、冒充官方分发」这件事做不成或不划算。
  开源代码本身可以被 fork，这一点不防，也防不住；Apache-2.0 + 署名附加条款负责法律层面。
- [ ] **R8 混淆**：开启 `isMinifyEnabled` + `isShrinkResources`，补齐 keep 规则；CI 归档 `mapping.txt`，
      不随 APK 公开。
- [ ] **运行时签名自检**：App 启动时比对自身签名证书的 SHA-256 与内置值（通过 `BuildConfig` 在发版 CI 中注入）；
      不一致就把「重打包」标记带进服务端认证，服务端可以拒绝这类客户端连接（可配置）。
      本地 debug 构建不受影响。
- [ ] **更新链路防劫持**：见第 2 节的三重校验，这是防止有人通过中间人推送二改包的关键。
      （v0.19.0 起改为 SHA-256 + 包名 / 版本 / 签名证书校验，见 v0.19.0 第 5 节。）
- [ ] **清单收尾**：关闭 `usesCleartextTraffic`（改为 network security config，只给明确的局域网调试放行）；
      确认 `allowBackup=false`（已是）；确认 token 存储使用 EncryptedSharedPreferences（已用 security-crypto）。
- 不做：在 APK 里硬编码更新 URL 加密、字符串加密这类措施。URL 本身是公开信息，加密只能拖慢对方几分钟，
  真正起作用的是签名校验。（理由见下方 ADR）
- 验收：release 包反编译后类名已混淆；用其他证书重签的包，启动时被检出并上报；
  更新篡改测试全部通过。

### 4. 波形库加载提速

- 改造前现状：波形**存在云端**（服务端数据库 `library_patterns` 表），App **没有任何本地缓存**，
  每次进入波形页都重新请求第一页。
- 实测：服务端查库约 3–8 ms，本机回环 1 ms；从外网经 CDN 访问，一次 HTTPS 请求要 2.5–3.4 秒
  （主要耗在 DNS、TLS 握手，以及每次都新建的 OkHttpClient——见下）。慢在网络，不在库。
- [x] **本地缓存 + 后台刷新（stale-while-revalidate）**：已落地——默认视图按账号哈希缓存到本地 JSON，
      进入页面先秒显示缓存，再静默重验；刷新失败保留缓存且不报错。
- [x] **共享 HTTP 客户端**：`PatternApi` 复用 `ApiClient.defaultClient()` 的连接池与 TLS 会话（见第 5 节）。
- [x] **条件请求**：`GET /patterns` 返回强 `ETag`，App 携带 `If-None-Match`，未变更时 304，几乎不传数据。
- [x] **切页面不重载**：进程级仓库在 App 启动时加载一次，切页只读内存/磁盘缓存，不再发请求。
- 验收：第二次进入波形页时首屏 < 100 ms（读缓存）；离线时仍能浏览缓存；
  后台刷新拿到新数据后正确合并，喜欢、收藏、删除、撤销等写操作立即反映到缓存中。

### 5. 波形库缓存、暂停/继续与循环轮数编辑

- [x] **进程级波形库缓存（含共享 OkHttp 连接池）+ 暂停/继续状态机 + 全局红色悬浮球 + 备注入口与循环轮数编辑**。
  已落地：仓库按连接/账号绑定，进 App 即预载，切页不再请求，仅启动时静默刷新一次；
  暂停冻结任务时间线并停止全部输出，继续从断点恢复（仅手机端可达，AI/relay 不可见）；
  悬浮球默认开启、需“显示在其他应用上层”权限、失败静默降级；
  非内置波形可在详情页修改循环轮数（1–60，总时长 ≤ 10 分钟，服务端校验）。

## v0.19.0

### 1. 吮吸档位文案自然化

- 问题：「吮吸 - 玩具预设」的 4/5/6 键仍是暂定名「节奏 06 / 07 / 08」，「吮吸 - 自由组合」的模式 7 是「节奏 B」，
  与其他档位的自然表述不一致（见 `docs/实施记录-樱趣-v0.14.md` 记录的已知不一致）。
- [ ] 玩具预设：「节奏 06」→「颤动」、「节奏 07」→「深吸」、「节奏 08」→「先短后长」；
      自由组合：「节奏 B」→「规律吮吸」。只改文案，协议字节（byte4 06/07/08、模式 7）不变。
- 验收：两个面板都不再出现「节奏 0x / 节奏 B」，界面测试覆盖。

### 2. 开发者模式只影响协议调试

- 问题：关闭「开发者模式」后，「协议调试」消失的同时「管理」也一起消失；预期是开关只影响协议调试。
- [ ] 「管理」入口只看账号身份（owner + 账号登录），与开发者模式无关。
- 验收：回归测试覆盖「开发者模式关 + owner → 管理可见、协议调试不可见」，修复前失败、修复后通过。

### 3. AI 接入页去掉失效 token 计数

- [ ] 删除「另有 x 个已撤销或过期的 token 未显示」这一行；失效 token 照旧不在列表中显示。

### 4. 子页面刷新按钮统一

- 问题：「管理」「AI 接入」右上角是刷新图标，「波形库」是文字「刷新」按钮，同一操作两种样式。
- [ ] 统一为波形库现有的文字按钮样式（`TextButton` +「刷新」），子页面头部共用一处实现。

### 5. App 内检查更新（GitHub Releases + 镜像源）

- 问题：「检查更新」只是打开 GitHub Releases 网页，用户看不到有没有新版本、也看不到更新说明；
  国内直连 GitHub 下载慢或失败。
- **与 v0.18.0 第 2 节的关系**：v0.18.0 第 2 节规划的是「服务端发布签名清单（`latest.json` + Ed25519）」路线，
  尚未实施。v0.19.0 由项目所有者改定为「**直接读 GitHub Releases + 镜像源**」路线，**取代** v0.18.0 第 2 节的
  清单 / Ed25519 部分，不再需要服务端或发版 CI 生成清单。v0.18.0 第 2 节中「APK 签名证书与当前已安装 App 一致才安装」
  的要求保留，并入本节；冷启动静默检查、`min_supported` 强制更新本版不做。
- 设计：
  - 检查：请求 GitHub `releases/latest`，失败时依次走支持 API 代理的镜像；展示版本号、发布日期、大小和**完整更新说明**。
  - 下载源：GitHub 官方 + 若干公共镜像（第三方服务，随时可能失效）。点「下载更新」时对全部源并发做小范围测速，
    剔除失效或返回非 APK 内容的源，按速度排序，把最快的源交给**系统 DownloadManager** 下载；
    下载失败或长时间无进度时自动换下一个源；应用内轮询下载进度，**实时显示进度、速度和来源**，可取消。
  - 完整性不依赖镜像可信：下载完成后校验文件大小、GitHub 提供的 SHA-256，再校验包名、versionCode 递增、
    签名证书与已安装 App 一致，任一不符**自动删除安装包**。
  - 权限（所有者定案，**零新增权限**）：更新包由 DownloadManager 写入 App 专属外部目录
    （`setDestinationInExternalFilesDir`，任何 Android 版本都不需要存储权限）；App 不自己发安装 intent，
    下载完成后引导用户点系统「下载完成」通知安装，安装由系统应用发起，因此不声明 `REQUEST_INSTALL_PACKAGES`、不需要 FileProvider。
    已知限制：AOSP 13 及以下的系统安装器会把「点通知安装」归到发起下载的 App（`EXTRA_ORIGINATING_UID`），
    未声明该权限会中止安装（Android 14 起改为归到系统「下载」应用）；厂商 ROM 行为可能不同。
    这些设备上的零权限兜底是「在浏览器中打开 Release 页面」，界面在 Android 13 及以下额外提示。
- 验收：版本比较、Release 解析（含 digest 缺失时从说明中取 SHA-256）、镜像测速排序与失效剔除、
  系统下载失败 / 停滞 / 校验失败换源、全部失败报错、包校验不过删除、系统下载管理器不可用时提示浏览器兜底、
  取消下载（同时移除系统下载）均有单元测试（DownloadManager 经接口 fake）；
  界面测试覆盖可下载 / 下载中 / 校验中 / 下载完成（引导点通知安装，含 Android 13 及以下提示）/ 已最新。
